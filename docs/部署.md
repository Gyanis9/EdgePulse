# EdgePulse 部署

## 1. 构建与运行产物

```bash
git submodule update --init --recursive
conan create 3rd/AsynGyanis/packaging/conan --build=missing \
  -s compiler.cppstd=23 -s build_type=Release -o "&:with_mysql=True"
conan install . --build=missing -s compiler.cppstd=23 -s build_type=Release
cmake --preset release
cmake --build --preset release --parallel
```

产物：

- `build/release/edgepulse-server`：后端可执行体。
- `frontend/dist`：前端构建产物；`bash scripts/build-web.sh` 会刷新到未跟踪的 `web/`。
- `migrations/`：启动时自动应用；不要手工改已应用文件的校验和。升级到 P7 会应用 `V19__enterprise_identity.sql`，创建 `sys_api_token`、`sys_idempotency`、`sys_user_mfa` 与令牌菜单；P8 继续应用 `V20__agent_certificate_renewal.sql`，给 `biz_node` 增加当前/上一枚证书字段并创建 `biz_agent_certificate` 历史表；P9 应用 `V21__control_plane_lease.sql`，创建 `sys_lease` 并插入 `control-plane` 行；P10 继续应用 `V22__firmware_rollout.sql`（发布/波次/目标表、任务关联列与节点已安装版本）与 `V23__firmware_rollout_wave_unique.sql`（发布内波次下标唯一）。生产升级前先做数据库备份，迁移失败时进程拒绝启动。多实例同时启动时由 MySQL `GET_LOCK` 串行化迁移，见 5.1。

## 2. 配置与秘密

复制 `config/prod.yaml.example` 为未跟踪的 `config/prod.yaml`，按环境改端口、监听地址、MySQL/Redis 主机与 `web_root`。

秘密只从环境变量读取：

| 变量 | 用途 |
|---|---|
| `EDGEPULSE_DB_PASSWORD` | MySQL 口令 |
| `EDGEPULSE_REDIS_PASSWORD` | Redis 口令 |
| `EDGEPULSE_OPS_BEARER_TOKEN` | 运维口 Bearer |
| `EDGEPULSE_AGENT_FINGERPRINT` | 允许注册的 Agent 证书 SHA-256 |
| `EDGEPULSE_INITIAL_PASSWORD` | 新建用户与重置密码表单的默认初始口令（预填、可改；不落库、不写日志） |
| `EDGEPULSE_UDP_TELEMETRY_SECRET` | UDP 遥测 HMAC 共享密钥；启用 UDP 时必填，至少 16 字节 |
| `EDGEPULSE_OIDC_CLIENT_SECRET` | OIDC 客户端密钥；公共客户端可留空 |
| `EDGEPULSE_MFA_KEY` | 两步验证主密钥，base64 编码的 32 字节；未配置时设置、启用、关闭与换发恢复码返回 503，已启用账号的登录校验也会失败；生产必须单独配置并纳入秘密备份 |

仓库零明文凭据；不要把口令写进 YAML、命令行参数、镜像层或 Git。

**默认管理员口令（必须立即处理）**：迁移 `V2__seed.sql` 会在全新库（SQLite 与 MySQL 相同）插入超级管理员 `admin` / `admin123`。它不区分开发档与生产档，`EDGEPULSE_INITIAL_PASSWORD` 只影响新建用户与重置表单的预填，不会改这个账号。任何对外可达的实例在首次登录后必须立刻修改该口令；在改密前不要让 8080/8443 暴露到公网。本阶段不强制首次改密，P11/P12 会补强制改密或阻断，P12 对外验收前会先轮换该口令。

### 两步验证主密钥

`EDGEPULSE_MFA_KEY` 是 TOTP 秘密的 AES-256-GCM 密钥，也是恢复码 HMAC 的键；同一套数据库上的所有实例必须使用同一个值，否则一个实例签发的秘密在另一个实例无法校验。

```bash
# 生成 32 字节随机密钥；只写入环境变量或秘密管理系统
openssl rand -base64 32
```

- 非空但 base64 解码后不是 32 字节时，进程启动直接报配置错误，错误文案不回显密钥内容。
- 未配置时，`/api/auth/mfa/setup`、`/enable`、`/disable` 与 `/recovery-codes` 返回 503；已经启用的账号在登录挑战阶段无法通过校验，管理员可在用户管理里重置该账号的两步验证。状态查询与管理员重置不依赖该密钥。
- 多实例部署必须启用共享 Redis：登录挑战、待启用秘密与每用户尝试计数都在缓存中；只用进程内缓存时，设置或挑战只落在签发请求的实例，跨实例会失败。
- 本阶段没有密钥轮换、`key_version` 迁移或 AAD 绑定。丢失或更换密钥后，已启用账号的 TOTP 与恢复码都不可用，只能逐账号重置；请把该密钥与数据库备份分开、按生产秘密管理，并记录到灾难恢复手册。
- 两步验证是用户自助启用，不存在租户级强制开关；需要统一强制时应在组织流程或后续策略功能中解决，不要把它写成当前能力。
- Compose 样例已在 `deploy/docker/.env.example` 与 `docker-compose.yml` 中声明 `EDGEPULSE_MFA_KEY`，默认留空；要使用两步验证时在未跟踪的 `deploy/docker/.env` 填入 `openssl rand -base64 32` 的结果再启动。systemd 部署写进 0600 的 `/etc/edgepulse/edgepulse.env`。

默认监听端口开发档与生产样例一致：8080 HTTP、8443 TCP/UDP、9443 mTLS、9100 运维口。开发档 `ops_address` 为 `127.0.0.1`，只允许本机抓取；生产样例改成 `0.0.0.0`，便于容器或 Prometheus 跨网络抓取，端口仍是 9100 且 `/metrics` 仍需 Bearer。只在本机抓取时保持回环，不要为了省事把运维口暴露到公网。

## 3. 证书

开发档：

```bash
bash scripts/dev-certs.sh
```

生成 CA、服务器证书、Agent 客户端证书与一组“陌生 CA”证书，放在未跟踪的 `var/certs/`。Agent 指纹写入 `var/certs/agent-fingerprint.txt`。

生产档把证书放到 `cert_dir` 指向的目录，至少需要：

- `server.pem` / `server-key.pem`：8443 与 9443 共用。
- `ca.pem`：9443 接受 Agent 客户端证书的信任锚（服务器链根）。

Agent 侧的 `ca_file` 不是这份 `ca.pem` 的简单副本：它既要验证 9443 服务器证书链，也要验证续期接口返回的 Agent 证书链。使用独立 Agent CA 时，`ca_file` 必须是拼接信任包，同时包含服务器链根与所有可能签发 Agent 证书的 CA（当前 CA 与轮换中的新 CA）；只放 9443 根会让续期证书链校验失败并按不可重试的安装错误停止续期。

启用 Agent 自动签发（`edgepulse.agent_ca.enabled: true`）时：

| 配置 | 默认值 | 说明 |
|---|---|---|
| `edgepulse.agent_ca.enabled` | `false` | 打开后控制面按 CSR 为 Agent 签发与续期证书 |
| `edgepulse.agent_ca.certificate_file` | `var/certs/ca.pem` | 签发 CA 证书；9443 监听开启时必须就是它的信任锚 `cert_dir/ca.pem`，或指纹包含在拼接信任包里 |
| `edgepulse.agent_ca.key_file` | `var/certs/ca-key.pem` | 签发 CA 私钥；独立路径、仅服务账号可读、POSIX 0600 或更严 |
| `edgepulse.agent_ca.validity_days` | `30` | 新证书有效期，1–3650 天；使用固定续期提前量时必须大于该值 |
| `edgepulse.agent_ca.overlap_hours` | `24` | 旧指纹重叠窗口，1–168 小时；实际截止取旧证书 notAfter 与「当前时间 + 窗口」的较小值 |

- `certificate_file` 与 `key_file` 不能是同一个文件；CA 证书必须带 `basicConstraints=CA:TRUE` 且私钥与证书配对。启动时如果 9443 监听器开启，会按 SHA-256 指纹核对签发 CA 是否在 `cert_dir/ca.pem` 的信任库里，不在就拒绝启动，避免签出 9443 自己都不认的证书。
- `key_file` 必须放在公开证书卷之外的独立路径（生产样例为 `/etc/edgepulse/agent-ca-key.pem`），不要与 `server-key.pem`、`ca.pem` 一起挂进容器或镜像。代码在 POSIX 上加载时检查权限，组或其他用户可读会直接拒绝启动；Windows 依赖数据目录 ACL。
- 开发档的 `scripts/dev-certs.sh` 已生成开发 CA 与 `ca-key.pem`，`config/dev.yaml` 直接复用同一对文件；生产不要复用开发 CA。

生成独立的生产 CA（示例）：

```bash
umask 077
openssl ecparam -name prime256v1 -genkey -noout -out /etc/edgepulse/agent-ca-key.pem
openssl req -x509 -new -key /etc/edgepulse/agent-ca-key.pem -sha256 -days 3650 \
  -subj "/CN=EdgePulse Agent CA" \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign" \
  -out /etc/edgepulse/agent-ca.pem
chmod 600 /etc/edgepulse/agent-ca-key.pem
```

独立 CA 部署时，9443 的 `ca.pem` 与节点的 `ca_file` 都要拼接两份证书：服务器链根（验证 9443 服务端证书）和 Agent CA（验证客户端/续期证书）。节点侧示例：

```bash
cat /etc/edgepulse/server-root.pem /etc/edgepulse/agent-ca.pem > /etc/edgepulse/ca.pem
chmod 644 /etc/edgepulse/ca.pem
```

CA 轮换顺序（独立 CA 部署）：

1. 生成新的 Agent CA 证书与私钥，旧 CA 保持签发。
2. 先把新 Agent CA 追加到每台节点的 `ca_file`，并把新 CA 追加到控制面 9443 的 `ca.pem`；节点在下一次加载身份或重启后生效。此时签发方仍是旧 CA，现有连接不受影响。
3. 确认节点仍在线上，再切换 `agent_ca.certificate_file` 与 `key_file` 指向新 CA，重启控制面。
4. 让节点自动续期或走 `rebind` 换成新 CA 签发的证书；确认新证书能完成 9443 握手与心跳。
5. 全部节点换证后，从节点 `ca_file` 与 9443 `ca.pem` 移除旧 CA，并重启节点使信任包生效。

漏掉第 2 步会让第 3 步之后的续期证书无法通过节点侧链校验；Agent 会记录无法链接到配置 CA 的 ERROR 并停止自动续期，旧证书到期后节点离线。CA 私钥泄露时立即停用内部 CA、吊销受影响节点证书并要求重新入场。

Agent 连接 9443 时必须带客户端证书与私钥；无证书或陌生 CA 在 TLS 握手阶段被拒。

### Agent 注册与证书

Agent 侧配置在 `edgepulse.agent` 下：

```yaml
edgepulse:
  agent:
    fingerprint: ""            # 可选：额外的固定指纹白名单，空表示只依赖 CA 链
    enrollment_mode: required  # off 或 required；生产使用 required
    heartbeat_interval_seconds: 30
    heartbeat_timeout_seconds: 90
    offline_sweep_seconds: 30
```

- `off`：开发档默认。新节点和换证书只靠 mTLS 链校验与指纹，不要求一次性令牌。
- `required`：新节点首次注册必须持 `enroll` 令牌；已有节点更换证书必须持 `rebind` 令牌；同指纹重注册不需要令牌。`enroll` 令牌不能用于已有节点，`rebind` 令牌不能创建新节点，缺令牌或令牌不可用返回 403。
- 令牌有效期必须在 300 到 2592000 秒之间；明文只在签发响应出现一次，列表只返回 `active/used/expired/revoked` 状态。

生产上线步骤：

1. 节点首次注册前，用管理员会话调用 `POST /api/enrollment-tokens`（`action` 为 `enroll`，建议用 `nodeName` 限定该节点），把响应里的 `token` 交给 Agent；Agent 在 `/api/agent/register` 的 `enrollmentToken` 字段带上它。
2. 更换 Agent 证书时先签发 `rebind` 令牌，再用新证书注册；不要复用旧令牌，每枚令牌只能消费一次。
3. 注册成功后 `GET /api/nodes/:id` 可读 `certNotAfter` 与 `certRevokedAt`；吊销证书会清空指纹、把节点置为离线，并以 1008 关闭该节点已建立的 Agent WebSocket 连接。
4. 超过 `heartbeat_timeout_seconds` 没有心跳的在线节点会被置为离线并生成系统离线告警，恢复心跳后自动销案。

### Agent 自动续期

启用内部 CA 后，Agent 侧用以下配置控制自动续期（两份打包模板已带默认值）：

```yaml
agent:
  certificate:
    renewal_enabled: true       # 使用外部 CA 时置 false，不启动续期循环
    renew_before_days: 0        # 0..90；0（默认）按 max(25% 生命周期, 24h) 计算
    renewal_check_seconds: 3600 # 60..86400，到期判断周期
```

- `renewal_enabled` 默认 true；置 false 后 Agent 不启动续期协程，只在启动日志记录一次，证书到期前必须按 `rebind` 流程手工换证。使用外部 CA、或控制面未启用 `edgepulse.agent_ca` 的部署应关闭它，避免每轮续期都收到 503 并按退避重试。
- 续期窗口按规范取 `max(25% 当前证书生命周期, 24h)`，生命周期由证书自身的 `notBefore` 与 `notAfter` 计算；`renew_before_days: 0` 表示使用该公式。配置非 0 时作为覆盖值，只有严格小于证书生命周期才生效；否则 Agent 记录 ERROR 并回退到规范窗口。固定提前量时必须保证控制面 `agent_ca.validity_days` 大于它，否则服务端签回的新证书会被按不可重试的配置错误拒绝安装。使用自动窗口时 `agent_ca.validity_days` 必须大于 1 天：1 天证书装好后剩余有效期不可能超过 24 小时窗口，安装会被按不可重试错误拒绝。
- Agent 启动后立即做一次到期判断，之后每 `renewal_check_seconds` 复查。进入窗口后生成新的 P-256 私钥与 CSR，调用 `POST /api/agent/certificate/renew`；服务端签回后先校验 PEM 标签、到期时间、公钥配对、CA 链与规范窗口，全部通过才原子替换证书与私钥（私钥 0600），随后在进程内热切换 HTTP 与 WebSocket，不重启进程、不改节点标识。
- 安装前把旧证书与私钥留成 `.bak`，并写 `证书路径.install-pending` 标记；如果进程死在两次替换之间，下次启动会按标记用 `.bak` 回退。首次安装（原本没有证书）时没有 `.bak`，标记会保留，进程因身份加载失败拒绝启动，需要人工放回证书后清理标记。如果服务端已经完成轮换、Agent 却还没装上新证书，重启时会出示重叠窗口内的旧证书；`required` 模式按同证书软重登记放行，不需要令牌，也不会把旧指纹提回当前值。
- 失败处置：403 表示节点已被吊销或需要重新准入，Agent 记 ERROR 并停止自动续期，必须重新签发 `rebind` 令牌、用新证书重新注册并重启服务；其余可重试失败（网络、5xx、408/409/425/429）按 5、10、30、60、300 秒退避后重试。签发成功后如果安装失败，Agent 会用同一份签发结果和待装私钥重试安装，不会重新申请证书；证书链、密钥配对或有效期这类不可重试错误会记录可操作原因并停止续期，避免服务端 active 被反复轮换而挤掉 Agent 实际持有的证书。HTTP 400 在默认序列上最长等待 20 分钟（300 秒 × 4），日志会打印实际毫秒数。
- 安装成功后 HTTP 或 WebSocket 任一通道重载失败时，Agent 不回退磁盘文件，而是保留新证书并按较短间隔复查重载；进程此时重启也会直接加载新的一对。
- 续期成功后状态库写入新的 `cert_fingerprint` 与 `cert_expiry`；节点详情里旧指纹出现在 `previousCertFingerprint`，在 `previousCertNotAfter` 之前仍可完成心跳、命令与遥测，到期或吊销后立即 403。
- 关闭内部 CA 时，已启用续期的节点会收到 503 并按可重试失败退避直到证书到期；这类节点应设置 `agent.certificate.renewal_enabled: false`，或按 `rebind` 流程在到期前换证。

## 4. 本地运行

```bash
bash scripts/run-dev.sh
```

脚本会确保证书与 `var/ops-token` 存在，导出运维令牌与 Agent 指纹，然后前台启动 `edgepulse-server --config config/dev.yaml`。

默认端口：8080 HTTP、8443 TCP/UDP、9443 mTLS、9100 运维口；UDP 遥测默认关闭，启用后监听 9555/UDP。详见 [架构](架构.md)。

UDP 遥测在 `config/prod.yaml` 中打开：

```yaml
edgepulse:
  udp_telemetry:
    enabled: true
    address: 0.0.0.0
    port: 9555
```

并设置 `EDGEPULSE_UDP_TELEMETRY_SECRET`（至少 16 字节）。数据报格式与签名算法见 [API](API.md) 的 UDP 遥测一节；Compose 已映射 9555/UDP 并把该环境变量透传进容器。

OIDC 登录在 `config/prod.yaml` 中按需打开：

```yaml
edgepulse:
  oidc:
    enabled: true
    issuer: https://idp.example.com
    client_id: edgepulse
    redirect_uri: https://console.example.com/api/auth/oidc/callback
    frontend_redirect: /login
    scopes: openid profile email
    allowed_email_domains: example.com
    auto_provision: true
    default_role_id: 2
    default_dept_id: 101
    tenant_code: default
```

`tenant_code` 决定 OIDC 外部身份落到哪个租户；外部账号只在该租户内按邮箱匹配或自动创建。租户由平台管理员在“系统管理 → 租户管理”创建，默认租户编码 `default` 承接升级前数据。

并在 IdP 侧登记同一个 `redirect_uri`；`issuer` 与 `redirect_uri` 必须是 HTTPS 或本机回环。Compose 已把 `EDGEPULSE_OIDC_CLIENT_SECRET` 透传进容器。

边缘反向代理在 `config/prod.yaml` 中按需打开：

```yaml
edgepulse:
  reverse_proxy:
    enabled: true
    prefix: /edge
    upstream: http://device-api:9000
    strip_prefix: true
    require_session: true
    permission: ""
```

它只转发 HTTP 请求/响应，不透传 EdgePulse 的 Authorization/Cookie，也不代理 WebSocket 升级与大流式响应。

## 5. 生产环境

最小拓扑：

- 一台或多台 EdgePulse 实例，挂同一个 MySQL。多实例必须同时启用 Redis，并满足 5.1 的共享固件卷、唯一实例标识与证书分工。
- MySQL 8.x 建库 `edgepulse`，应用账号只需该库的 DML/DDL 权限。备份账号另需该库的 `SELECT` 权限与全局 `PROCESS` 权限（`mysqldump` 不加 `--no-tablespaces` 时）。
- Redis 7.x 用来放会话、验证码、登录失败计数、两步验证的挑战/待启用秘密/尝试计数、租户状态、实时扇出与 Agent 命令路由；启用时 `edgepulse.redis.enabled=true`。多实例共享 MFA 与跨实例命令必须启用 Redis。
- 反向代理/负载均衡负责 TLS 卸载时，后端仍建议保留 8443/9443 的 TLS 入口；Agent 必须直连 mTLS 端口。

启动顺序：

1. 数据库可连接、迁移目录可读。
2. 若启用 Redis，Redis 可连接；连接失败时启动失败而不是静默退化成内存。
3. 服务器证书、私钥与 CA 可读。
4. `/readyz` 返回 200 后再接入流量。

### 5.1 双实例 HA

仓库提供 `deploy/docker/docker-compose.ha.yml`、`deploy/nginx/edgepulse.conf`、`deploy/prometheus/prometheus.ha.yml` 与 `deploy/systemd/edgepulse@.service`。拓扑是 nginx 对外 8080/8443/9443：8080 与 8443 做 L7 转发到 `edgepulse-1:8080`、`edgepulse-2:8080`，8443 由 nginx 终止 TLS；9443 只做 TCP 透传，mTLS 仍在实例上完成。两个应用容器不发布端口，共享 MySQL、Redis、只读配置与证书目录、固件公钥目录、Agent CA 私钥卷与 `firmware-data` 命名卷；配置是同一份 `prod.yaml`，入口脚本按 `EDGEPULSE_INSTANCE_ID` 生成各自的可写副本。

前置条件：

- MySQL 8.x：两个实例连同一个库、同一个账号，账号只需该库的 DML/DDL 权限。启动迁移前实例会持有 `GET_LOCK('edgepulse:migrations:<库名>', 30)`，拿不到锁或 `GET_LOCK` 出错时拒绝启动；SQLite 不参与 HA。
- Redis 7.x：必须 `edgepulse.redis.enabled=true`。会话、验证码、登录失败计数、MFA 挑战与尝试计数、租户状态缓存、实时扇出与跨实例 Agent 命令路由都依赖它；不启用时两个实例各自内存，跨实例行为不成立。
- 共享固件目录：两个实例的 `firmware_dir` 必须指向同一份存储（Compose 用 `firmware-data` 卷，systemd 用同一台机器的共享路径）；本地卷会让 A 上传的固件在 B 下载不到。固件灰度同样依赖共享卷：leader 派发的历史版本要能被任意实例上的 Agent 下载。
- 固件灰度单飞：推进循环只在 leader 上每 5 秒跑一拍，发布头用 `version` 比较交换；`check-ha-stack.py` 额外断言同一目标跨多个 tick 只有一条任务与一条命令。leader 切换可能让某一拍延后，不应把短暂停推进误判成卡死。
- 唯一实例标识：每个实例显式配置 `edgepulse.instance_id`（1–128 字符、不含空白），同时存活的实例不能重复；留空时按 `hostname-pid-random` 生成，能启动但日志、租约与信封无法稳定区分。Compose 入口脚本把字符集进一步收紧为 `[A-Za-z0-9._-]`，`/`、空格与中文会被拒绝启动；systemd 直接读 YAML，只受应用的空白限制。所有实例需 NTP 对齐，时钟偏差超过 TTL 会出现双 leader。
- 证书分工：应用证书目录只放 `ca.pem`、`server.pem`、`server-key.pem`；nginx 证书目录只放 `server.pem`、`server-key.pem`；Agent CA 私钥通过 `EDGEPULSE_AGENT_CA_KEY_FILE` 指向宿主机 0400 文件，不进入任何证书目录。启用 `agent_ca` 时 `ca.pem` 必须包含签发 CA，否则启动期指纹核对失败。
- 共享秘密：同一数据库上的实例使用相同的 `EDGEPULSE_DB_PASSWORD`、`EDGEPULSE_REDIS_PASSWORD` 与 `EDGEPULSE_MFA_KEY`；运维令牌可以按实例不同，但 Prometheus 的 Bearer 要与被抓取实例一致。
- 浏览器 Origin：nginx 把 8443 发布到宿主机时，控制台 Origin 带端口，`security.allowed_origins` 必须包含 `https://console.example.com:8443`（`config/prod.yaml.example` 已同时列出 443 与 8443）；只走外层 443 负载均衡时改成 `https://console.example.com`。缺少该值时 `/api/ws` 升级返回 403。
- Agent CA 私钥可选：启用控制面内部 CA 时准备 `EDGEPULSE_AGENT_CA_KEY_FILE` 并用 `--profile agent-ca` 启动；使用外部 CA 或 `agent_ca.enabled=false` 时不设置私钥、不带 profile，`ca-key-init` 不会启动，`app` 对它的依赖是 `required: false`。

systemd 多实例：

```bash

cmake --preset debug
cmake --build --preset debug --target edgepulse-server
bash scripts/build-web.sh

# 单元以 User=edgepulse 运行；已有该用户时跳过创建
id -u edgepulse >/dev/null 2>&1 || \

sudo install -d -m 0755 /opt/edgepulse /opt/edgepulse/web /opt/edgepulse/migrations
sudo install -m 0755 build/debug/edgepulse-server /opt/edgepulse/edgepulse-server
sudo cp -r web/. /opt/edgepulse/web/
sudo cp -r migrations/. /opt/edgepulse/migrations/

sudo cp deploy/systemd/edgepulse@.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo install -d -m 0755 /etc/edgepulse
# /var/lib/edgepulse 由单元的 StateDirectory=edgepulse 创建并归 edgepulse 所有。
# 若单元没有这一项或要手工预建，用：
# sudo install -d -o edgepulse -g edgepulse -m 0750 /var/lib/edgepulse
sudo cp config/prod.yaml.example /etc/edgepulse/edgepulse-1.yaml
sudo cp config/logging.yaml /etc/edgepulse/logging.yaml
sudo install -m 0600 /dev/null /etc/edgepulse/edgepulse-1.env
sudoedit /etc/edgepulse/edgepulse-1.yaml   # instance_id、http/https/agent/ops 端口、MySQL/Redis 地址、allowed_origins
sudoedit /etc/edgepulse/edgepulse-1.env    # 写 EDGEPULSE_DB_PASSWORD、EDGEPULSE_REDIS_PASSWORD 等秘密
sudoedit /etc/edgepulse/logging.yaml       # 滚动 sink 的 directory 改成 /var/lib/edgepulse/logs

# 证书与密钥按前置条件放置：/etc/edgepulse/tls 只放 ca.pem、server.pem、server-key.pem，
# 私钥 0400 且属主为 edgepulse；固件公钥放 /etc/edgepulse/firmware-keys；启用 agent_ca 时
# 把配置里的 key_file 改到 /etc/edgepulse/agent-ca-key.pem（0400，属主 edgepulse）。
sudo install -d -m 0755 /etc/edgepulse/tls /etc/edgepulse/firmware-keys

curl -fsS http://127.0.0.1:9100/readyz
```

- 第二台按同样步骤创建 `/etc/edgepulse/edgepulse-2.yaml`、`edgepulse-2.env` 并启动 `edgepulse@edgepulse-2`；跨主机时两台各自安装二进制、`web/`、`migrations/` 与单元。
- 单元实例名 `%i` 对应 `/etc/edgepulse/%i.yaml` 与 `/etc/edgepulse/%i.env`（0600，秘密只写这里）。同机多实例时各配置的 `http_port`、`https_port`、`agent_port`、`ops_port` 必须互不冲突。
- 共享固件：`ProtectSystem=strict` 只放开 `ReadWritePaths=/var/lib/edgepulse`，所以跨主机共享存储必须挂在 `/var/lib/edgepulse/firmware`（默认 `firmware_dir`）或其子目录；挂到 `/srv`、`/mnt` 等其它路径会被拒绝写入。必须挂到别处时加 drop-in，同时把配置里的 `firmware_dir` 改成同一路径：
  `sudo install -d -m 0755 /etc/systemd/system/edgepulse@edgepulse-1.service.d`，写入 `[Service]` 段和 `ReadWritePaths=/srv/edgepulse-firmware`，再 `sudo systemctl daemon-reload`。
- `StateDirectory=edgepulse` 创建 `/var/lib/edgepulse` 并交给服务用户；`ExecStartPre` 再建 `/var/lib/edgepulse/logs`，`ReadWritePaths=/var/lib/edgepulse` 允许固件、日志与运行时配置写入。`logging.yaml` 里滚动 sink 的 `directory` 要写绝对路径 `/var/lib/edgepulse/logs`，写相对路径会落到只读的 `/opt/edgepulse`。容器编排把 `logging.yaml` 复制到每个实例的运行时配置目录，日志落在 `/app/var/logs`。
- nginx 用实例的真实地址，不要用 Compose 的 `edgepulse-1`/`edgepulse-2` DNS 名；复制 `deploy/nginx/edgepulse.conf` 后分别改 `http {}` 与 `stream {}` 里的 upstream：

  ```nginx
  # http {} 内：浏览器 8080/8443 转发到实例 8080
  upstream edgepulse_http {
      server 10.0.0.11:8080 max_fails=2 fail_timeout=5s;
      server 10.0.0.12:8080 max_fails=2 fail_timeout=5s;
      keepalive 32;
  }

  # stream {} 内：Agent 9443 TCP 透传，mTLS 在实例上完成
  upstream edgepulse_agent {
      server 10.0.0.11:9443 max_fails=2 fail_timeout=5s;
      server 10.0.0.12:9443 max_fails=2 fail_timeout=5s;
  }
  ```

  跨主机时把地址换成两台实例的实际内网 IP；同机部署时用 `127.0.0.1` 加两套不同端口，upstream 的端口同步改。systemd 部署没有 Docker DNS，只能用静态地址或自建 DNS，且 upstream 主机名只在启动时解析一次。改完先 `sudo nginx -t`，通过后再 `sudo systemctl reload nginx`。nginx 不读取 `/readyz`，只按 `max_fails`/`fail_timeout` 被动摘除，实例恢复后等 `fail_timeout` 到期再看下一请求。
- `TimeoutStopSec=40s` 与 Compose 的 `stop_grace_period` 一致：先让 `/readyz` 变 503，再排空在途请求。

滚动升级：

1. 一次只动一个实例。`docker compose stop edgepulse-1` 或 `systemctl stop edgepulse@edgepulse-1`，等 `/readyz` 变 503、进程退出；nginx 在连接失败后把流量与新的 Agent 连接转给另一台。
2. 用新镜像重建或替换二进制后启动该实例，`/readyz` 返回 200 后等 `fail_timeout`（5 秒）过去，nginx 会重新尝试该上游；容器重建换了 IP 时还要 reload 或重启 nginx 让 DNS 重新解析。确认 `sys_lease` 的 holder 与 fence 符合预期。
3. 观察一轮心跳、命令与告警，再重复处理第二个实例。不要同时重启两台，否则 nginx 没有可用上游，Agent 长连接与在途请求都会中断。
4. 迁移只追加（V21 只新建 `sys_lease`，V22/V23 只新增灰度表、任务关联列与节点版本列），旧版本可在回滚窗口内继续运行；回滚前先确认没有依赖新表或灰度功能在使用，停止所有灰度发布并清空 `sys_lease` 的 holder。

故障切换：

- 优雅停机：停止请求先让 `/readyz` 503 并立即清空自己的 holder，随后排空在途请求；下一台按 5 秒周期接手。2026-10-25 实测接管 1.75 秒，fence 由 1 升到 2。
- 崩溃：`SIGKILL` 后旧 holder 留在租约行直到 TTL（15 秒）过期，下一台在 2 个 TTL（30 秒）内接手，fence 递增。实测 16.71 秒，fence 由 2 升到 3；重启的旧 leader 就绪后不抢占仍在续约的新 holder。
- 验证：`SELECT holder, fence, expires_at, updated_at FROM sys_lease WHERE name='control-plane';`，再查 `SELECT 1` 与两台 `/readyz`；跨实例会话与命令路由不要靠单台日志判断。

限制与取舍：

- nginx 用 `max_fails=2 fail_timeout=5s` 做被动摘除，普通接口在连接失败、超时或 502/503/504 时换上游；故障刚发生时可能有一个请求先收到 502 或超时。WS 与 SSE 只对 `error timeout` 重试。开源 nginx 没有主动健康检查，也不读取 `/readyz`；upstream 主机名在启动时解析一次，容器重建换 IP 后要 reload 或重启 nginx。
- 应用不信任 `X-Forwarded-For`，登录限频、MFA 来源 IP 绑定与审计看到的是 nginx 地址；同一代理后的用户共享这些计数。需要真实来源时在网关层限频并保留单一代理出口，详见第 5 节的“反向代理与来源 IP”。
- 全局限流按实例计数，N 个实例的实际总速率是各自配置之和；按上例配置并在网关层按租户或令牌另做限流。
- MySQL、Redis 与 nginx 仍是单点；本阶段不做存储层高可用、跨地域多活与自动分片。租户配额、按租户/按 Agent 的数据面限流与命令并发上限不在本阶段。

### 反向代理与来源 IP

服务端只取 TCP 连接的直接对端地址作为来源 IP，不解析 `X-Forwarded-For`、`Forwarded` 或 `X-Real-IP`，也没有可信代理白名单。

- 在负载均衡、CDN 或反向代理之后，登录限频、MFA 挑战的来源 IP 绑定与登录审计看到的都是代理地址；同一代理后的所有用户共享这些计数与绑定条件。
- 需要按真实来源限频或绑定 MFA 时，给控制面保留稳定的单一代理出口，或让代理直接透传到后端；不要依赖客户端自报的头。多条代理出口会把不同用户打散成新来源，也会让限频阈值失去意义，必要时在代理层限频并调整应用侧参数。
- 来源 IP 不是身份依据，审计中的来源地址只能作为线索。更多边界与取舍见 [SECURITY.md 已知边界](../SECURITY.md#已知边界)。

### API 令牌运维

- 在“系统管理 → API 令牌”或 `POST /api/system/api-tokens` 创建，明文 `ep_api_...` 只在响应或一次性对话框出现一次；关闭对话框后无法找回，只能轮换。把它直接写入目标系统的秘密存储，不要落在脚本、镜像、日志或工单里。
- `scopes` 只授予自动化真正需要的权限码；令牌每次请求都会与 owner 当前权限取交集，角色权限被收回后令牌同步缩小，全部收回即 401。令牌吊销或过期、owner 或租户停用都会立即失效。
- 默认有效期 30 天，可按需设置 300 到 31536000 秒。到期前用 `POST /api/system/api-tokens/{id}/rotate` 轮换：旧明文保留 1 小时重叠窗口，新明文立即生效；`expiresAt` 不变，所以轮换不能替代续期，临近到期时要新建令牌。
- 怀疑泄露时调用 `DELETE /api/system/api-tokens/{id}` 吊销；记录只标记 `revokedAt` 不删除，列表仍可见，便于审计。创建与轮换只接受浏览器会话，令牌会话调用返回 403；吊销缺 `system:token:remove` 返回 403，标识不存在、已吊销、跨租户，或令牌会话处置他人/超出自身 scope 的令牌返回 404。
- 令牌身份不是平台管理员。`/api/auth/me` 可用于自省；`/api/auth/routes`、`/api/auth/logout`、其他只要求登录的浏览器接口与浏览器 WebSocket 会拒绝令牌，也不能修改账户口令；它适合调用带明确权限码的业务 API，不适合替代人工登录。
- 建议按环境、按用途分令牌（例如 CI 只读、发布写入），不要把同一枚令牌发给多个系统；当前没有按令牌的独立速率限制，滥用仍受全局令牌桶与 owner 权限约束。

### 写请求幂等与表增长

- 带有效 Bearer 与 `Idempotency-Key` 的 `POST/PUT/PATCH/DELETE` 会写入 `sys_idempotency`，保留 24 小时；行数约等于“24 小时内带幂等键的写请求数”，不是令牌数或业务实体数。响应正文上限 256 KiB，大响应不会落表。
- 后台保留期协程会定期删除 `expires_at` 已过的行，索引 `idx_idempotency_expires` 服务该清理；同键请求到来时也会先删除自己的过期行。多实例部署时保留期清理只在 leader 上执行（见 [架构](架构.md) 第 9.2 节），follower 不重复扫描；leader 切换后由新 leader 接管，短暂空窗不会让过期行永久累积。
- 断言：升级后旧格式指纹的缓存行不会与新请求匹配，24 小时内同键重试会得到 409 而不是重放；这是有意的安全选择。
- 认证、Agent、WebSocket、SSE、流式固件上传、API 令牌、注册令牌、用户/租户写入与反向代理前缀不进入幂等表，避免一次性明文或口令被缓存。需要重试这些接口时，应按业务查询确认结果，不要依赖 `Idempotency-Key`。
- 处理中占位有 90 秒租约；进程崩溃留下的行在租约过后可被接管，接管按至少一次语义执行。业务侧仍应保证重复执行安全。

| `server.parser_limits.maximum_body_size` | 16 MiB | 256 MiB |

监听端口两边相同；端口、监听地址与 `server` 段在启动时生效，热重载不会改变。生产档的限流与连接超时仍要在目标容量上复核，样例中的数值只是起点。

多实例部署的完整要求见 5.1：共享 MySQL + Redis、唯一的 `edgepulse.instance_id`、共享固件目录、nginx 与证书分工。`config/prod.yaml.example` 已包含 `instance_id` 与 `ha.enabled`；开发档保持单实例，租约循环仍运行但立即当选。

### Webhook 出站安全（SSRF）

告警 Webhook 由租户管理员填写，服务端在创建或修改渠道时解析主机并逐个检查地址：

- 默认拒绝回环、私网、CGNAT、组播、保留与文档示例段，以及 IPv6 回环、唯一本地、组播与文档段；IPv4-mapped IPv6 按内嵌 IPv4 判断，只有内嵌私网或保留 IPv4 的映射地址被拒（例如 `::ffff:8.8.8.8` 这类公网映射地址不在拒绝范围）。
- `localhost`、`*.localhost` 与 `*.local` 这类本机或局域网别名默认拒绝；打开开关后交给解析器，解析结果仍按地址段检查。
- 云元数据地址与主机名（如 `169.254.169.254`、`169.254.170.2`、`100.100.100.200`、`fd00:ec2::254`、`fd20:ce::254`、`metadata.google.internal`、`instance-data`、`metadata.tencentyun.com`）始终拒绝，不受下面的开关影响。
- 整个 IPv4 链路本地段 `169.254.0.0/16` 与 IPv6 链路本地段 `fe80::/10` 也始终拒绝：云元数据端点都落在这两段里，不能靠枚举已知端点来兜底。
- 每次投递前还会复检一次；命中上述地址时不发请求，只记一条失败投递并累加 `edgepulse_webhook_ssrf_rejections_total`。

自建内网网关（例如 `http://10.0.0.8/hook`）需要在 `config/prod.yaml` 显式打开：

```yaml
edgepulse:
  security:
    allow_private_webhooks: true
```

默认是 `false`。打开后放行普通私网、回环、CGNAT、组播、保留与文档示例段（含 IPv6 唯一本地地址），但仍拒绝云元数据主机名、已知元数据端点（例如 `100.100.100.200`、`fd00:ec2::254`、`fd20:ce::254`）与 IPv4/IPv6 链路本地段（`169.254.0.0/16`、`fe80::/10`）。它不是「只放行 RFC1918」的窄开关：生产打开前应确认主机或容器网络层已有出站防火墙与域名白名单，不要只靠这个开关。开发档 `config/dev.yaml` 为本地验收 Webhook 打开了它。

校验与实际连接之间存在 DNS 重绑定窗口：引擎客户端会再次解析域名，可能拿到与校验时不同的地址。高安全环境不要只依赖这个开关，应在主机或容器网络层配置出站防火墙与域名白名单。

这道检查只覆盖 Webhook 的 HTTP(S) 出站。SMTP 邮件渠道的 `smtp://`、`smtps://` 与 `starttls://` 端点不经过 HTTP 地址校验，必须由运维填写可信服务器并自行确认网络可达范围；不要把它当成已受 SSRF 防护的入口。

反向代理的 upstream 是运维配置，只校验协议与 userinfo，不受本节的私网限制。

### 口令策略、登录锁定与全局限流

建号、管理员重置与用户改密共用同一套口令策略，配置在 `edgepulse.security` 下：

```yaml
edgepulse:
  security:
    password_min_length: 10          # 允许 8 到 64；低于 8 或高于 64 启动即报错
    password_require_complexity: true # 要求同时包含大写、小写、数字与符号
    login_failure_window_seconds: 900 # 60 到 86400
    login_max_failures: 5             # 1 到 100
    login_lock_seconds: 900           # 60 到 86400
```

生产档用 10 位加复杂度；开发档 `config/dev.yaml` 放宽为 8 位且不要求复杂度，历史种子账号与本地验收脚本因此无需改口令。`password_min_length` 的合法范围是 8–64，低于 8 或高于 64 会在启动时直接报错，8 是允许的最小值。长度按 UTF-8 码点计，一个中文字符算一个字符而不是三个字节。策略只约束新建、重置与修改，既有账号仍可用原口令登录。

口令策略不回溯校验存量口令：策略上线后，低于新下限的弱口令在完成轮换之前仍然可以登录。运维不能假定策略会自动让它们失效，必须在启用策略后主动完成轮换——管理员通过 `PUT /api/system/users/{id}/password` 重置，或用户通过 `PUT /api/auth/password` 改密；重点排查历史种子账号、共享账号与长期未改密的账号。

登录失败先按来源 IP 限频，再按账号累计：窗口内连续失败达到 `login_max_failures` 后写入锁定截止时刻，触发锁定的那次失败仍返回统一的 401，下一次尝试起返回 423；文案里的分钟数是 `login_lock_seconds` 折算的锁定时长（向上取整），不是剩余时间。该账号在任何 IP 上用正确口令也会被锁定挡住；管理员重置口令会同时清空失败计数与锁定。成功登录会清空账号与 IP 两侧的失败计数。锁定截止时刻过期后列值不会自动清空，登录按当前时间比较后放行，成功登录或管理员重置时清零；管理端只在截止时刻仍在将来时显示「已锁定」。

连接与限流配置在顶层 `server` 下，全部在启动时生效，热重载不会改变：

```yaml
server:
  limits:
    idle_timeout_ms: 75000    # 两次请求之间的空闲；0 关闭
    read_timeout_ms: 60000    # 相邻两次读取的最长间隔；0 关闭
    write_timeout_ms: 60000   # 处理器与发送响应的时限；0 关闭
  quic:
    idle_timeout_seconds: 30  # h3 传输层空闲超时，1 到 3600
  parser_limits:
    maximum_body_size: 16777216
  rate_limit:
    requests_per_second: 0.0  # 整数与小数均可；0 关闭全局限流
    burst_capacity: 1.0       # 令牌桶容量，必须不小于 1
```

`server.limits.read_timeout_ms` 与 `write_timeout_ms` 作用于 HTTP、HTTPS、Agent、运维口与 h3 监听器，`idle_timeout_ms` 只对 HTTP、HTTPS、Agent 与运维口生效。h3 的空闲计时由 QUIC 传输层的 `Configuration::idleTimeout` 决定，取 `server.quic.idle_timeout_seconds`（1 到 3600，默认 30 秒），不读 `HttpServerLimits::idleTimeout`，因此调大 `idle_timeout_ms` 不会延长 h3 连接。

`server.parser_limits.maximum_body_size` 是 Agent 与运维口的正文上限，这两类监听器只收心跳、状态与指标等小正文。公开 HTTP、HTTPS 与 h3 接受固件上传，解析上限取 `maximum_body_size` 与 `edgepulse.maximum_firmware_bytes` 的较大者，启动日志会打印两类监听器各自生效的字节数。`requests_per_second` 接受整数与小数两种写法（`10` 与 `10.0` 等价），写成非数字、NaN 或无穷会在启动时直接报错；大于 0 时 HTTP、HTTPS 与 h3 共用同一个令牌桶，超速请求返回 429 与 `Retry-After`，设为 0 则不注册限流中间件。存活与就绪探针 `/healthz`、`/readyz`、`/api/health` 与 `/api/probe/` 前缀不参与限流，避免编排器在限流期间把进程误判为不健康。生产环境建议按实例容量设置非零值，并让 `burst_capacity` 覆盖正常的并发突发。

注意：

- `.env`、`deploy/prometheus/ops-token`、`config/prod.yaml` 与证书都不进版本库，且都在 `.dockerignore` 中，不会进入构建上下文。
- Compose 把 `../../config` 只读挂到 `/app/config`；缺少 `prod.yaml` 时入口脚本把样例复制到 `/var/lib/edgepulse/prod.yaml` 再启动，不往挂载里写。
- `docker-compose.yml` 是单实例/开发编排，不提供故障切换；HA 用 5.1 的 `docker-compose.ha.yml`。单实例编排只把 `var/certs` 下的 `ca.pem`、`server.pem`、`server-key.pem` 三个文件只读挂到 `/etc/edgepulse/tls`，`ca-key.pem` 不会进入容器。启用 Agent 内部 CA 时，把 `key_file` 指到单独挂载的宿主机文件。Docker secret 默认以 0444 挂载，而控制面在 POSIX 上拒绝组或其他用户可读的 CA 私钥，不能直接当 `key_file` 用；改用只读 bind mount。以下路径都以 `deploy/docker` 为当前目录，与上面的 Compose 步骤一致。在 `docker-compose.yml` 的 `edgepulse.volumes` 列表中追加一行：

```yaml
      - ./secrets/agent-ca-key.pem:/run/secrets/agent_ca_key:ro
```

服务端配置指向该挂载点：

```yaml
edgepulse:
  agent_ca:
    enabled: true
    certificate_file: /etc/edgepulse/tls/ca.pem
    key_file: /run/secrets/agent_ca_key
```

宿主机侧先放出文件，再查出镜像内 `edgepulse` 的 uid/gid 并收紧权限（下面的 `999` 只是示例，实际值以 `id` 输出为准）：

```bash
umask 077
mkdir -p secrets
install -m 0400 /secure/agent-ca-key.pem secrets/agent-ca-key.pem
docker compose run --rm --no-deps --entrypoint id edgepulse   # 输出 uid=999(edgepulse) gid=999(edgepulse)
sudo chown 999:999 secrets/agent-ca-key.pem
```

宿主机上的 CA 证书与私钥必须配对，且证书就是 9443 的信任锚：单实例样例把 `ca.pem` 挂到 `/etc/edgepulse/tls/ca.pem`，`certificate_file` 指向同一份文件，启动时控制面按 SHA-256 指纹核对，不一致会拒绝启动。文件属主必须是容器内运行 uid（上面的 `999`），权限 `0400` 或更严；`0440`、`0640` 因组或其他用户可读会被控制面拒绝。

验证：`docker compose config >/dev/null` 能解析新增的 bind mount 源路径；`docker compose up -d` 后 `docker compose exec edgepulse stat -c '%a %u:%g' /run/secrets/agent_ca_key` 应输出 `400 999:999`，`docker compose exec edgepulse id -u` 应输出同一个 uid；`docker compose logs edgepulse` 应出现「Agent 内部 CA：已启用」，且没有「CA 私钥文件权限过宽」。bind mount 的源文件必须提前存在，否则 Docker 会按目录创建并导致启动失败。`0600` 也可用，但 `0400` 已满足只读挂载的最小权限。CA 私钥不要写进镜像层或 Compose 的 `environment`，宿主机上也不要放进版本库或公开证书卷；`deploy/docker/secrets/` 已在 `.gitignore` 与 `.dockerignore` 中。
- Compose 样例已声明 `EDGEPULSE_MFA_KEY` 并默认留空；要使用两步验证，先在未跟踪的 `deploy/docker/.env` 用 `openssl rand -base64 32` 生成并填入该变量，再启动 Compose，否则容器内的设置、启用、关闭与换发恢复码按 503 处理。
- `ops_address` 必须是 `0.0.0.0`，否则 Prometheus 容器抓不到 `edgepulse:9100/metrics`；该口仍需 Bearer。
- 运行镜像已预建 `/app/var/logs`，默认 `logging.yaml` 可写；前端产物、迁移与配置都在镜像内。
- 全栈验收：`python scripts/check-docker-stack.py --build`（复用镜像时去掉 `--build`）。脚本会自备随机秘密、证书与测试配置，覆盖登录、自定义角色、节点、审计落库、Redis 会话跨重启、Prometheus 抓取、真实 OTel collector 与 SIGTERM 优雅停机，结束后只清理本项目的容器与卷。
- 双实例编排用同一目录的 `docker-compose.ha.yml`，不启动上面这份单实例 Compose；完整步骤、证书分工与故障演练见 5.1。双实例验收：`python scripts/check-ha-stack.py --require-docker`（Docker 不可用时 `--require-docker` 直接失败，不带该参数才 SKIP）。脚本默认复用已构建的 `edgepulse:ha` 镜像，缺失时加 `--build`。

## 8. systemd

`deploy/systemd/edgepulse.service` 是单实例模板：

1. 二进制放 `/opt/edgepulse/edgepulse-server`，前端产物放 `/opt/edgepulse/web`，迁移放 `/opt/edgepulse/migrations`。
2. 配置放 `/etc/edgepulse/config.yaml`，秘密放 `/etc/edgepulse/edgepulse.env`（0600）。
3. `systemctl daemon-reload && systemctl enable --now edgepulse`。
4. 用 `curl http://127.0.0.1:9100/readyz` 判断就绪；`journalctl -u edgepulse -f` 看日志。

单元文件启用了 `ProtectSystem=strict`、`NoNewPrivileges` 与只写 `/var/lib/edgepulse`，固件目录必须在可写路径内。配置目录若放 `logging.yaml`，文件日志的 `directory` 要用绝对路径（如 `/var/lib/edgepulse/logs`），否则日志只进 journal。

多实例用 `deploy/systemd/edgepulse@.service`：实例名 `%i` 对应 `/etc/edgepulse/%i.yaml` 与 `/etc/edgepulse/%i.env`，`StateDirectory=edgepulse` 创建 `/var/lib/edgepulse`，`ExecStartPre` 再建 `/var/lib/edgepulse/logs`，`TimeoutStopSec=40s` 覆盖排空。同机多实例的端口必须互不冲突；`firmware_dir` 必须共享，且要落在 `ReadWritePaths=/var/lib/edgepulse` 内（默认 `/var/lib/edgepulse/firmware`），挂到其它路径需按 5.1 加 `ReadWritePaths` drop-in。启动、日志与滚动步骤见 5.1。

本机已在一个特权 systemd 容器中真机启动该单元：服务进入 `active`、`/readyz` 返回 ready、`systemctl stop` 后 `ExecMainCode=1` 且 `ExecMainStatus=0`。真实主机上的内核与 cgroup 差异仍需在目标发行版复核；`edgepulse@.service` 尚未在真实 systemd 主机上启动验证。

- Prometheus 抓取 `edgepulse:9100/metrics`，Bearer 从 `credentials_file` 读取；样例见 `deploy/prometheus/prometheus.yml` 与 `prometheus.ha.yml`。

## 10. 热重载、就绪与停机

- `edgepulse.hot_reload=true` 时监听配置目录；会话 TTL、验证码 TTL/限流热生效，监听地址与端口需重启。容器编排的配置副本在 `/var/lib/edgepulse/runtime`，修改共享的 `/app/config/prod.yaml` 后要重启实例才会重新生成。
- `/readyz` 依次检查五项依赖：数据库探针（每 2 秒）、启停状态、缓存探针（每 10 秒，启用 Redis 时为 PING）、实时事件总线（订阅与发布连接健康）、固件目录可写（每 10 秒写删探针文件）。任一不就绪返回 503 与第一条原因，判定顺序固定；`/api/health` 与 `/healthz` 只表示进程存活。
- 收到停机请求先把启停状态置 false，`/readyz` 立即变 503；随后按 HTTP/HTTPS/mTLS/QUIC/Ops 顺序排空，最后停止事件循环。Compose 的 `stop_grace_period` 与 systemd 的 `TimeoutStopSec` 都是 40 秒。
- 滚动发布时先摘流量、等 `/readyz` 变 503，再发停止信号；新实例 `/readyz` 200 后由负载均衡接回流量。单机没有监听句柄交接，零 5xx 依赖负载均衡的滚动机型；双实例步骤见 5.1，nginx 只做被动摘除，不读取 `/readyz`。

## 11. 备份与恢复

备份归档是一个 `tar.gz`，内含 `manifest.json`、数据库快照（SQLite 为 `db/edgepulse.db`，MySQL 为 `db/edgepulse.sql`）、`firmware/` 与 `config/`。`manifest.json` 记录归档格式、创建时间、驱动、最高 `schema_migrations` 版本以及每个文件的 SHA-256；恢复时逐文件核对，哈希不符直接拒绝。

SQLite 备份可以在服务运行中执行，工具用 SQLite 在线备份接口取一致快照：

```bash
python scripts/backup.py --driver sqlite --db-path var/edgepulse.db \
  --firmware-dir var/firmware --config-dir config \
  --output backups/edgepulse-$(date +%Y%m%d-%H%M%S).tar.gz
```

MySQL 备份用 `mysqldump --single-transaction --routines --triggers`，口令只从 `EDGEPULSE_DB_PASSWORD` 读入 `MYSQL_PWD`，不出现在命令行、日志与清单里。未设置该变量时工具按免密方式连接（例如 socket 认证）；口令账号忘记设置会得到 `Access denied`，工具会在 stderr 提示当前按免密连接：

```bash
read -rsp '数据库口令: ' EDGEPULSE_DB_PASSWORD; export EDGEPULSE_DB_PASSWORD
python scripts/backup.py --driver mysql \
  --db-host 127.0.0.1 --db-port 3306 --db-name edgepulse --db-user edgepulse \
  --firmware-dir /var/lib/edgepulse/firmware --config-dir /etc/edgepulse \
  --output backups/edgepulse-$(date +%Y%m%d-%H%M%S).tar.gz
```

归档路径已存在时备份会拒绝覆盖，保留唯一文件名即可。`--config-dir` 只收非敏感文件：`prod.yaml`、`*.env`、私钥（`*.key`、`*.p12`、`*.pfx` 与 PEM 私钥）以及 `.git`、日志不会进入归档。证书与运维令牌仍要单独托管，不要和数据库备份放同一份未加密介质。

恢复前先停止服务，避免运行中的进程继续写库或持有文件句柄。SQLite 恢复会在替换前删除目标库旁的 `-wal`、`-shm`、`-journal`；如果这些文件被占用而删不掉，恢复会报错退出，说明服务没有停干净。先做一次 dry-run，参数与正式恢复保持一致：

```bash
python scripts/restore.py --archive backups/edgepulse-YYYYmmdd-HHMMSS.tar.gz --driver sqlite \
  --db-path var/edgepulse.db --firmware-dir var/firmware --config-dir config --force --dry-run
```

校验通过后去掉 `--dry-run` 执行恢复。目标数据库、固件目录或配置文件非空时默认拒绝覆盖，确认要覆盖再加 `--force`；目标库的迁移版本高于归档时始终拒绝。dry-run 即使报告正式恢复会被拒绝也以 0 退出，只有真正执行恢复时才返回非零。

```bash
python scripts/restore.py --archive backups/edgepulse-YYYYmmdd-HHMMSS.tar.gz --driver sqlite \
  --db-path var/edgepulse.db --firmware-dir var/firmware --config-dir config --force
```

MySQL 恢复要求目标库已存在，账号具备建表、写入与触发器权限。把 `db/edgepulse.sql` 通过管道交给 `mysql`，口令同样走 `MYSQL_PWD`：

```bash
read -rsp '数据库口令: ' EDGEPULSE_DB_PASSWORD; export EDGEPULSE_DB_PASSWORD
python scripts/restore.py --archive backups/edgepulse-YYYYmmdd-HHMMSS.tar.gz \
  --driver mysql --db-host 127.0.0.1 --db-port 3306 --db-name edgepulse --db-user edgepulse \
  --firmware-dir /var/lib/edgepulse/firmware --config-dir /etc/edgepulse --force
```

MySQL 容器往返测试（可选，需 Docker，镜像需已在本机）：

```bash
python scripts/backup_restore_mysql_test.py
```

脚本起一次性 MySQL 8.4 容器，写入迁移版本与探针数据，执行备份、篡改、恢复后核对恢复值，结束时删除容器；`--mysql-image` 可改用其他镜像。`backup.py`/`restore.py` 的 `--mysql-container NAME` 会用 `docker exec` 在容器内执行 `mysqldump`/`mysql`，此时不需要宿主机客户端，也不读 `--db-host`/`--db-port`。该选项仅用于测试或受控运维环境：`docker exec -e MYSQL_PWD=...` 会让口令出现在本机进程参数里，生产请用宿主机客户端或受限执行环境。

恢复动作：SQLite 先写同目录临时文件再 `os.replace` 原子替换；MySQL 导入 dump；固件先解到目标同级的临时目录，成功后替换，旧目录保留为 `.bak` 直到整次恢复成功；配置逐文件原子替换，不动归档外的本地文件。恢复完成后启动服务并检查 `/readyz`：

```bash
# 启动服务（按部署方式选择 systemd、容器或直接运行）
curl -fsS http://127.0.0.1:9100/readyz
```

备份里带着 `schema_migrations`，恢复后不要手工改迁移版本；启动时迁移校验和必须与迁移文件一致。数据库里的固件记录只存元数据，固件文件丢失会导致下载 404，所以恢复后还要抽查固件下载。

### 11.1 双实例 HA 的备份与恢复

备份可以在两个实例运行时执行：`scripts/backup.py` 的 MySQL 分支用 `mysqldump --single-transaction --routines --triggers`，对 InnoDB 取一致性快照，不锁表。但数据库快照与固件目录、配置文件不是同一个事务，要求严格一致时先停写或对固件卷做同一时刻的快照；备份期间新上传的固件可能不在归档里。脚本读宿主机上的固件与配置目录：Compose 的固件在 `firmware-data` 命名卷里，先导出到宿主机目录（或改用 bind mount），MySQL 可用 `--mysql-container "$(docker compose -f docker-compose.ha.yml ps -q mysql)"` 直接读运行中的容器。

恢复必须同时停掉两个实例和共享 Redis，否则存活实例会继续续约租约并向恢复前的库写入，Redis 里恢复前的会话、失败计数与 MFA 挑战也会继续生效：

1. 停两个实例与 Redis：`docker compose -f docker-compose.ha.yml stop edgepulse-1 edgepulse-2 redis`，或 `sudo systemctl stop edgepulse@edgepulse-1 edgepulse@edgepulse-2` 后单独停 Redis。等进程退出；Compose 用 `docker compose -f docker-compose.ha.yml ps -a` 确认三个容器都是 exited（不带 `-a` 只能看到运行中的容器）。确需清空 Redis 时执行 `docker compose -f docker-compose.ha.yml exec -T redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli --no-auth-warning FLUSHALL'`（Redis 已停止时先 start 再 exec，清完再 stop），或删除 `redis-data` 卷（`docker compose -f docker-compose.ha.yml down` 后 `docker volume rm edgepulse-ha_redis-data`）。只停应用不停 Redis 时，旧会话仍能通过鉴权、登录失败计数与账号锁定继续生效、两步验证挑战仍可被消费；这些状态不在备份归档里，恢复后可能与数据库中的用户/租户状态不一致。
2. 确认租约不再续约：连续两次查询 `SELECT holder, fence, expires_at, updated_at FROM sys_lease WHERE name='control-plane';`，`updated_at` 应保持不变。优雅停机已把本实例的 holder 清空；若上一次是崩溃退出，holder 会留到 TTL（15 秒）过期，也可以手工清成空行：
   `UPDATE sys_lease SET holder='', expires_at=NULL, updated_at=UTC_TIMESTAMP() WHERE name='control-plane';`
3. 用 `scripts/restore.py --driver mysql` 恢复。systemd/宿主机路径示例，先跑一次 `--dry-run`：

   ```bash
   python scripts/restore.py --archive backups/edgepulse-YYYYmmdd-HHMMSS.tar.gz \
     --driver mysql --db-host 127.0.0.1 --db-port 3306 --db-name edgepulse --db-user edgepulse \
     --firmware-dir /var/lib/edgepulse/firmware --config-dir /etc/edgepulse --force --dry-run
   ```

   确认后去掉 `--dry-run`。Compose 的 MySQL 用 `--mysql-container "$(docker compose -f docker-compose.ha.yml ps -q mysql)"`，配置目录用 `--config-dir` 指向 `EDGEPULSE_HA_CONFIG_DIR`（默认 `../../config`）；固件在 `firmware-data` 命名卷里，`restore.py` 只写宿主机目录，先把卷导出到宿主机目录供 `--firmware-dir` 使用，恢复后再写回卷，否则只恢复了数据库。`restore.py` 通过重命名固件目录做替换，`firmware_dir` 本身是 NFS 或 bind 挂载点时 `os.replace` 会失败；应把共享存储挂到父目录、让固件目录是挂载点内的普通子目录，或先恢复到普通目录再同步。归档里的 `sys_lease` 行也会被写回；恢复完成后再次执行上面的 UPDATE，清掉归档里残留的 holder 与 `expires_at`，fence 保留，否则旧备份中的 leader 可能在新实例启动后仍被视为有效 holder。
4. 只启动一个实例（`docker compose -f docker-compose.ha.yml up -d edgepulse-1` 或 `sudo systemctl start edgepulse@edgepulse-1`），等 `/readyz` 返回 200，再查 `sys_lease` 确认 `holder` 是该实例且 fence 已递增。
5. 启动第二个实例前，先确认 `biz_command` 里没有遗留的 `running` 命令（Redis 丢失后没有实例会推进它们）；启动后等它的 `/readyz` 返回 200，nginx 在 `fail_timeout` 到期后把流量分给两台，Agent 重连或按 60 秒兜底轮询恢复命令通道。
6. Redis 不在备份归档里：会话、验证码、失败计数、实时扇出与在途命令都会丢失。浏览器需要重新登录，Agent 会在重连或轮询后恢复。

## 12. 固件签名

固件签名覆盖文件 SHA-256 的 32 字节原始摘要，算法标识为 `ed25519-sha256`，签名字节以标准 Base64 传输。上传时服务端验签，下载时把 `X-Firmware-Signature`、`X-Firmware-Key-Id`、`X-Firmware-Signature-Algorithm` 回给 Agent，Agent 可据此复核落盘文件。

1. 生成密钥对：`bash scripts/firmware-signing-keygen.sh prod-2026`。私钥写在未跟踪的 `var/firmware-signing-key.pem`，脚本拒绝覆盖已有私钥或同名公钥；key id 只允许字母、数字、点、下划线与连字符，不能含路径分隔符或 `..`。公钥写到 `config/firmware-keys/prod-2026.pem`。
2. 只把公钥分发到各实例的 `edgepulse.firmware.trusted_keys_dir`；私钥留在签名工作站或密钥管理系统，不进入镜像、备份与仓库。
3. 对固件签名：`bash scripts/sign-firmware.sh var/firmware-signing-key.pem <固件> prod-2026`，输出 `key=` 与 `signature=` 两行。
4. 上传时带两个请求头：`X-Firmware-Signature: <signature>` 与 `X-Firmware-Key-Id: prod-2026`。缺签名或缺 key id 的请求在收正文前就返回 400，不会写盘；只有写完文件后才做的验签（key 不受信任、摘要不符、签名格式不对）失败时返回 400，并删除已写入的成品。
5. 切换门禁：把 `edgepulse.firmware.require_signature` 改为 `true` 并重启。生产样例默认开启，且信任键目录为空时启动直接失败；目录要求写绝对路径。
6. 开启后未签名固件不能上传、部署或回滚，但已入库的历史未签名固件仍可被 Agent 下载。需要继续下发这些旧固件时，先重新上传带签名的同版本固件，再按新记录部署。
7. `GET /api/firmware/policy` 需要权限 `device:firmware:list`，返回 `{requireSignature, trustedKeyIds}`，用于确认当前实例加载了哪些公钥。

### 12.1 固件灰度发布

灰度发布在 `V22`/`V23` 迁移后自动可用，不需要新增配置项；它复用固件签名门禁、租户边界与 Agent 心跳。

1. 先在目标节点安装一个基线版本并等待心跳上报 `installedFirmwareVersion`，否则自动回滚没有历史版本，目标会记为 `rollback_unavailable`。
2. 在控制台固件页选择目标固件，点击“灰度发布”；勾选节点（勾选顺序即波次归属），填写累计波次百分比（默认 5/25/100，最后一波必须 100%），按需调整沉降、观察、单波上限、成功率、最大失败数、遥测新鲜度、超时动作与自动回滚。
3. `settleSeconds` 必须不小于两个 Agent 心跳周期（开发档心跳 10 秒时至少 20，生产样例 30 秒时至少 60）；`maxWaveSeconds` 不能小于沉降与观察窗口的较大值。`requiredFreshTelemetrySeconds` 要大于遥测上报周期，否则门控会一直等待新鲜遥测。
4. 创建后详情每 5 秒刷新；第一波目标达到 `healthy` 后自动派发第二波。门控失败且开启自动回滚时进入 `rolling_back`，逐目标重新下载并安装历史版本；回滚确认要求命令成功、任务 `installed` 且心跳版本等于历史版本。
5. 需要人工干预时使用暂停、恢复、提升、强制提升、中止与回滚。强制提升必须填写原因；回滚是重新下发，不是回滚槽位切换，强制签名部署下历史版本也必须已签名。
6. 排障顺序：先看发布详情的 `lastError` 与目标 `health.reason`，再查 `biz_firmware_rollout_target`（`status/command_id/task_id/health_json`）、`biz_firmware_task`（`rollout_id/wave_id/command_id`）与 `biz_command`。leader 每 5 秒推进一次，`listDueRollouts` 固定 `LIMIT 20`；大量积压时较新的发布会排队，这是 P11 的审计项。
7. 升级/回滚应用前先暂停或中止进行中的灰度；数据库迁移只追加，灰度表与任务关联列在旧版本上会被忽略，但旧版本不会推进灰度。HA 部署下所有实例共享同一份灰度表，只有 leader 落库；不要把推进循环改成每实例独立执行。

## 13. Agent（Linux）

生产 Agent 以 systemd 服务运行，发行包包含二进制、单元文件、安装/卸载脚本与配置模板。Windows 服务托管与安装包见第 14 节。

### 13.1 节点侧准备

Agent 配置模板默认读取以下文件：

| 文件 | 用途 |
|---|---|
| `/etc/edgepulse/ca.pem` | 节点信任包：至少包含 9443 服务器证书链的根，以及所有可能签发本节点证书的 Agent CA |
| `/etc/edgepulse/agent.pem` | 节点客户端证书 |
| `/etc/edgepulse/agent-key.pem` | 节点私钥，权限保持 0600 |

证书必须与控制面 `9443` 的信任链匹配，节点身份以叶证书 SHA-256 指纹绑定。独立 CA 部署时，节点的 `ca_file` 要把服务器链根与 Agent CA 拼在一起（`cat server-root.pem agent-ca.pem > ca.pem`），CA 轮换时先追加新 Agent CA 再切换签发方。开发环境先运行 `bash scripts/dev-certs.sh` 生成开发 CA，再用 `bash scripts/gen-agent-certs.sh <节点名> [--days <天数>] [--out-dir <目录>]` 为单个节点签发客户端证书。

启用控制面内部 CA 后，在 `agent.yaml` 里确认续期参数（模板默认已写入）：

```yaml
agent:
  certificate:
    renewal_enabled: true
    renew_before_days: 0
    renewal_check_seconds: 3600
```

`renew_before_days: 0` 按规范 `max(25% 生命周期, 24h)` 计算；配置固定值时必须小于证书有效期，并保证控制面 `agent_ca.validity_days` 大于该值。

续期会原地原子替换 `certificate_file` 与 `private_key_file`，所以这两个路径必须对 Agent 服务账号可写、目录可创建临时文件与 `.bak`，私钥保持 0600；只读挂载证书会让续期在安装阶段失败。控制面地址必须是 `https://`，明文测试配置不会启动续期循环。

首次注册需要在控制台签发一次性 `enroll` 令牌；已有节点更换证书时签发 `rebind` 令牌。安装器会创建 `/etc/edgepulse-agent/agent.env`（0600），其中以注释形式列出两个变量名：

```bash
#EDGEPULSE_AGENT_ENROLLMENT_TOKEN=
#EDGEPULSE_AGENT_REBIND_TOKEN=
```

去掉注释并填入令牌后重启服务。令牌只从环境变量读取，不写 YAML、不写日志、不写状态库；注册成功后清空对应变量。

### 13.2 打包

```bash
# 在 Linux 上执行 Release 构建并打包
bash scripts/package-agent.sh --version 1.0.0

# 打包已有二进制（不做构建）
bash scripts/package-agent.sh --version 1.0.0 \
  --binary build/release/bin/edgepulse-agent --output /tmp/agent-package

# 同时签名：对归档 SHA-256 生成 <包名>.sig 与 <包名>.json
bash scripts/package-agent.sh --version 1.0.0 \
  --binary build/release/bin/edgepulse-agent --output /tmp/agent-package \
  --signing-key var/agent-package-key.pem --signing-key-id prod-2026
```

默认输出目录是 `build/agent-package`，生成 `edgepulse-agent-<version>-linux-<arch>.tar.gz` 与同名的 `.manifest.json`、`.checksums.sha256`；提供私钥时另有 `<包名>.sig` 与 `<包名>.json`。省略 `--binary` 时脚本只允许在 Linux 上执行 `cmake --preset release` 与 `cmake --build --preset release --target edgepulse-agent`；其他平台会直接拒绝，Windows 安装包见第 14 节。

包内顶层文件：

```text
edgepulse-agent
edgepulse-agent.service
install-agent.sh
uninstall-agent.sh
agent.yaml.example
manifest.json
checksums.sha256
manifest.sig（仅签名包）
```

`manifest.json` 的 `version` 与 `platform` 描述整包，`files` 数组按路径排序，逐项记录其余文件的 `path`、`size` 与 `sha256`。`checksums.sha256` 以 `sha256sum` 格式覆盖同一批数据文件，升级安装器据此复核归档。`manifest.sig` 覆盖 `manifest.json` 的摘要，是包内纵深防御。

Agent 的信任根是归档签名：`agent.update` 的 `sha256` 是归档文件本身的 SHA-256，`signature` 是 Ed25519 对该 32 字节摘要的签名。Agent 先验签再下载，并要求下载文件的摘要与之相等；归档内的 manifest、checksums 与数据文件因此一并获得认证。`<包名>.sig` 与 `<包名>.json` 描述归档，不进入归档；没有私钥时不生成任何签名旁路文件，未签名包只用于本地或手工安装。

### 13.3 安装

```bash
mkdir -p /tmp/edgepulse-agent
tar -xzf build/agent-package/edgepulse-agent-*.tar.gz -C /tmp/edgepulse-agent
sudo /tmp/edgepulse-agent/install-agent.sh
```

普通重装前先 `sudo systemctl stop edgepulse-agent`，再运行安装器替换二进制；安装器不会重启已在运行的进程，旧进程会一直持有旧二进制，直到下次重启。控制面下发 `agent.update` 时走 13.5 的升级流程，由安装器自己停启服务。

默认布局：

| 项目 | 默认路径 | 权限 |
|---|---|---|
| 二进制 | `/usr/local/bin/edgepulse-agent` | 0755 |
| 安装器副本 | `/usr/local/lib/edgepulse/install-agent.sh` | 0755 |
| systemd 单元 | `/etc/systemd/system/edgepulse-agent.service` | 0644 |
| 配置目录 | `/etc/edgepulse-agent` | 0750 |
| 配置文件 | `/etc/edgepulse-agent/agent.yaml` | 0600，仅在不存在时写入模板 |
| 环境文件 | `/etc/edgepulse-agent/agent.env` | 0600，仅在不存在时创建 |
| 状态目录 | `/var/lib/edgepulse-agent` | 0750，放 SQLite、固件与更新暂存 |
| 日志目录 | `/var/log/edgepulse-agent` | 0750 |

安装器参数：

| 选项 | 默认值 | 说明 |
|---|---|---|
| `--prefix DIR` | `/usr/local` | 二进制写入 `DIR/bin/edgepulse-agent` |
| `--config-dir DIR` | `/etc/edgepulse-agent` | 配置与环境文件目录 |
| `--state-dir DIR` | `/var/lib/edgepulse-agent` | 状态、固件与更新暂存目录 |
| `--log-dir DIR` | `/var/log/edgepulse-agent` | 日志目录 |
| `--no-start` | 关闭 | 只安装文件，不执行 `systemctl daemon-reload` 与 `enable --now` |

单元的关键项与服务约定一致：`Type=simple`，`ExecStart=/usr/local/bin/edgepulse-agent --config /etc/edgepulse-agent/agent.yaml --console`，`Restart=on-failure`、`RestartSec=5`，`EnvironmentFile=-/etc/edgepulse-agent/agent.env`，`LimitNOFILE=65536`，`NoNewPrivileges=true`，`ProtectSystem=strict`，`ReadWritePaths` 只放开配置、状态与日志目录，`PrivateTmp=true`。安装器会按 `--prefix`、`--config-dir`、`--state-dir`、`--log-dir` 替换单元中的 `ExecStart`、`EnvironmentFile` 与 `ReadWritePaths`，并把配置里的 `/usr/local/lib/edgepulse` 替换为 `<prefix>/lib/edgepulse`，默认值下与仓库中的模板一致。安装器自身也复制到 `<prefix>/lib/edgepulse/install-agent.sh`，配置里的 `agent.update.installer_script` 指向这个副本。

默认系统路径与启动服务需要 root。全部路径改到可写目录并加 `--no-start` 时，非 root 也可以只落文件；测试可用 `SYSTEMD_UNIT_DIR` 覆盖单元目录。已有 `agent.yaml` 与 `agent.env` 不会被覆盖。

安装完成后检查：

```bash
systemctl status edgepulse-agent
journalctl -u edgepulse-agent -f
```

```bash
sudo /tmp/edgepulse-agent/uninstall-agent.sh

# 一并删除配置、状态与日志
sudo /tmp/edgepulse-agent/uninstall-agent.sh --purge
```

路径参数与安装器一致；只删文件、不调用 systemd 时加 `--no-start`。单元或服务已经不存在时脚本仍会正常结束。

### 13.5 升级

控制面下发 `agent.update` 后由 Agent 与安装器协作完成升级，不需要人工停服务。正文示例：

```json
{
  "version": "1.1.0",
  "url": "/api/agent/update/download/0192f0c4",
  "sha256": "<归档 SHA-256，64 位小写十六进制>",
  "signature": "<Ed25519 对 sha256 摘要的签名，标准 Base64>",
  "signingKeyId": "prod-2026",
  "algorithm": "ed25519-sha256"
}
```

`manifest` 字段不再参与信任判断；即使控制面仍下发，也会被忽略。`version` 是本地升级状态与上报使用的标签，安装器等待的健康标记版本来自已认证归档里的 `manifest.json`，两者应保持一致。

1. Agent 读取 `agent.update.package_trusted_keys_dir` 里的 Ed25519 公钥，先对命令 `sha256` 的 32 字节摘要验证 `signature`，失败即拒绝且不下载；通过后从 `url` 流式下载到 `agent.update.staging_directory`，计算下载文件的 SHA-256 并要求与命令摘要相等。随后把待上报结果写入状态库，以脱离进程启动 `<prefix>/lib/edgepulse/install-agent.sh --upgrade <包> --health-timeout <秒> --state-dir <状态目录> --prefix <前缀>`，并退出当前进程。
2. 安装器在停止服务之前校验包内 `checksums.sha256`、manifest 版本与 `platform`；归档真实性已由 Agent 的签名检查建立。随后删除旧的 `update-health`、`update-rollback` 与 `update-expected`，把 `<prefix>/bin/edgepulse-agent` 备份为 `.previous`，停止 `edgepulse-agent.service`，只替换二进制。替换后、启动服务前写入 `<状态目录>/update-expected`（内容为 manifest 版本）。替换前任何一步失败时二进制不变，安装器会检查服务状态并用旧二进制重新拉起已停止的服务，然后以非零码退出。
3. 安装器启动服务，并在 `agent.update.health_timeout_seconds` 内等待 `<状态目录>/update-health` 出现且内容等于 manifest 版本。新版本 Agent 在首次成功心跳后写出该标记：有 `agent.update` 待上报结果时用成功结果替换此前“安装器已启动”的结果；手工升级没有待上报结果时，按 `update-expected` 的版本直接写健康标记。两种路径都会在版本匹配后删除 `update-expected`。
4. 成功时安装器删除 `.previous`、健康标记与 `update-expected`。超时、启动失败或健康标记版本不符时，安装器停止服务、恢复 `.previous`、删除 `update-expected`、写入 `<状态目录>/update-rollback`（内容为目标版本）并启动旧版本，然后以非零码退出；旧版本 Agent 在首次心跳后把该命令按失败写回结果队列（同样替换“安装器已启动”的结果）并删除回滚标记。若没有回滚标记但运行版本与升级目标版本不一致，Agent 也按失败上报，且不写健康标记；`update-expected` 与运行版本不符时只记 WARN 并保留标记，由安装器回滚。

升级只替换二进制，`agent.yaml`、`agent.env`、状态库、安装器副本与 systemd 单元保持原样。安装器日志固定写入 `<状态目录>/update-installer.log`（默认 `/var/lib/edgepulse-agent/update-installer.log`）；健康与回滚标记也在状态目录，安装器不写 SQLite，升级结果由 Agent 在首次心跳后补报。

手工复现同一条路径：

```bash
sudo /usr/local/lib/edgepulse/install-agent.sh --upgrade /tmp/edgepulse-agent-1.1.0-linux-x86_64.tar.gz \
  --health-timeout 60 --state-dir /var/lib/edgepulse-agent --prefix /usr/local
```

手工运行安装器只校验 `checksums.sha256`，不验归档签名；Ed25519 验签只在 Agent 下载后执行，手工升级只用于复现或救急。自动路径的归档真实性由 Agent 的签名检查建立，手工路径需要调用方自行确认归档来源。手工升级没有待上报的 `agent.update` 结果，新版本靠安装器写入的 `update-expected` 在首次成功心跳确认健康；版本与运行版本不符时不会写健康标记，安装器按超时回滚并清理该标记。

限制：安装器固定操作 `edgepulse-agent.service`，自定义 unit 名需要手工升级；升级包必须是 tar.gz，`checksums.sha256` 必须覆盖 `edgepulse-agent`，manifest 的 `platform` 必须与宿主架构一致（打包脚本按 `uname -m` 生成 `linux-x86_64` 或 `linux-aarch64`，不能在 aarch64 上安装 x86_64 包），版本必须能解析；`--upgrade` 不接受 `--no-start`；只有升级前后两个版本都包含本节的心跳确认逻辑时，回滚后的失败结果才会自动补报。

`agent.restart` 命令的结果先写入本地队列并尝试上报，之后才通过 `systemd-run --collect` 启动的 `systemctl restart edgepulse-agent` 重启服务，当前进程随即请求停止。启动器创建失败时只记 ERROR 并保持运行；服务端可能已收到成功结果，但不会发生重启。

## 14. Agent（Windows）

Windows 上 Agent 以服务控制管理器（SCM）服务运行：`edgepulse-agent.exe --service` 由 SCM 启动，服务名默认 `EdgePulseAgent`，账户默认 LocalSystem。`--service-name <name>` 指定 SCM 注册名（默认 `EdgePulseAgent`，只允许 ASCII 字母、数字、点、下划线与连字符，最长 256 个字符），安装器会把同一个名字写进服务命令行，自定义服务名不需要手工改二进制参数。`--service` 只在 Windows 构建中可用；在控制台直接运行会返回 1 并提示必须由 SCM 启动，`--service` 与 `--console` 同时出现按用法错误返回 2。服务进入 RUNNING 后，停止与关机控制只请求应用停止，服务先进入 STOP_PENDING 并递增检查点，工作线程收尾完成后置为 STOPPED；`run()` 返回非零时以服务专属退出码上报。

### 14.1 打包

```powershell
# 默认执行 cmake --preset release 并构建 edgepulse-agent，输出到 build\agent-package
powershell -ExecutionPolicy Bypass -File scripts\package-agent.ps1 -Version 1.0.0

# 打包已有二进制，不执行构建
powershell -ExecutionPolicy Bypass -File scripts\package-agent.ps1 -Version 1.0.0 `
  -Binary build\release\bin\edgepulse-agent.exe -Output $env:TEMP\agent-package

# 同时签名：对 zip 的 SHA-256 生成 <包名>.sig 与 <包名>.json
powershell -ExecutionPolicy Bypass -File scripts\package-agent.ps1 -Version 1.0.0 `
  -Binary build\release\bin\edgepulse-agent.exe -Output $env:TEMP\agent-package `
  -SigningKey var\agent-package-key.pem -SigningKeyId prod-2026
```

生成 `edgepulse-agent-<version>-windows-x86_64.zip`，顶层包含 `edgepulse-agent.exe`、`agent.yaml.example`、`install-agent.ps1`、`uninstall-agent.ps1`、`manifest.json` 与 `checksums.sha256`；签名包另有 `manifest.sig`。清单的 `files` 按路径排序，逐项记录 `path`、`size` 与 `sha256`。提供私钥时输出目录还写出 `<包名>.sig` 与 `<包名>.json`：前者是 zip 文件本身的 SHA-256 签名，后者记录 `version`、`platform`、`sha256`、`signature`、`signingKeyId` 与 `algorithm`，两者都不进入 zip。Agent 信任的是归档签名，包内 manifest 与 checksums 随归档一起获得认证；没有私钥时不生成签名旁路，未签名包只用于本地或手工安装。

### 14.2 目录与权限

| 项目 | 默认路径 | 权限 |
|---|---|---|
| 二进制 | `C:\Program Files\EdgePulse\Agent\edgepulse-agent.exe` | Users 读取/执行 |
| 安装脚本副本 | `C:\Program Files\EdgePulse\Agent\install-agent.ps1` | Users 读取/执行 |
| 配置文件 | `C:\ProgramData\EdgePulse\Agent\agent.yaml` | Administrators、SYSTEM 完全控制 |
| 证书目录 | `C:\ProgramData\EdgePulse\Agent\certs` | 同上 |
| 状态与日志 | `C:\ProgramData\EdgePulse\Agent`、`agent.log` | 同上 |
| 固件暂存 | `C:\ProgramData\EdgePulse\Agent\firmware` | 同上 |
| 固件公钥 | `C:\ProgramData\EdgePulse\Agent\firmware-keys` | 同上 |
| 升级暂存与包公钥 | `C:\ProgramData\EdgePulse\Agent\update`、`update\keys` | 同上 |

安装器只调整自己创建的目录与文件：数据目录关闭继承，只授予 Administrators（`S-1-5-32-544`）与 SYSTEM（`S-1-5-18`）完全控制；安装目录关闭继承后授予 Administrators 与 SYSTEM 完全控制、Users（`S-1-5-32-545`）读取/执行。不会修改 `Program Files` 或 `ProgramData` 本身的权限。任何一条 `icacls` 失败都会让安装中止并打印中文原因。

### 14.3 安装

```powershell
Expand-Archive build\agent-package\edgepulse-agent-1.0.0-windows-x86_64.zip -DestinationPath $env:TEMP\edgepulse-agent -Force
# 以管理员身份打开 PowerShell
powershell -ExecutionPolicy Bypass -File $env:TEMP\edgepulse-agent\install-agent.ps1
```

首次安装还没有证书时先加 `-NoStart`，按 14.4 准备证书与配置后再启动；直接启动会因身份加载失败而以中文错误中止。

安装器参数：

| 选项 | 默认值 | 说明 |
|---|---|---|
| `-InstallDir DIR` | `C:\Program Files\EdgePulse\Agent` | 二进制与安装脚本副本所在目录 |
| `-DataDir DIR` | `C:\ProgramData\EdgePulse\Agent` | 配置、证书、状态、日志、固件与升级暂存 |
| `-ServiceName NAME` | `EdgePulseAgent` | SCM 服务名 |
| `-NoStart` | 关闭 | 创建服务但不启动 |

升级模式另有 `-Upgrade <zip>`、`-HealthTimeout <秒>` 与 `-StateDir <目录>`，由 Agent 自动调用，普通安装不需要提供；详见 14.8。

`-InstallDir`、`-DataDir`（安装与卸载脚本）以及卸载脚本的 `-Purge` 目标必须是带盘符的绝对路径：拒绝盘符根目录、`%SystemRoot%`（含 `System32`）与 `C:\Users` 及其子目录，以及 `%ProgramFiles%`、`%ProgramFiles(x86)%`、`%ProgramData%`、用户目录等受保护根；位于 Program Files 或 ProgramData 时第一级目录必须是 `EdgePulse`，并且盘符下至少要有两级目录。安装目录也不能位于数据目录之下。自定义这两个参数时，新生成的 `agent.yaml` 会把模板里的默认前缀替换为实际路径；已有 `agent.yaml` 一律保留，不会被覆盖。

安装器先停止同名服务（存在时；若服务仍在 StartPending 会先等待其落定），再替换二进制；随后创建服务（已存在时用 `sc.exe config` 更新启动命令），启动命令为 `"<InstallDir>\edgepulse-agent.exe" --config "<DataDir>\agent.yaml" --service --service-name "<ServiceName>"`，启动类型 `auto`，并写入失败恢复动作：

```powershell
sc.exe failure EdgePulseAgent reset= 86400 actions= restart/5000/restart/10000/restart/30000
```

自定义 `-ServiceName` 时，安装器把同一个名字同时用于 `sc.exe create`/`config` 与 `--service-name`；只改 SCM 服务名而不传这个参数，服务会因控制处理函数注册失败而无法启动。最后启动服务并等待其进入 RUNNING，再等两秒用 `sc.exe queryex` 复核状态与 `SERVICE_EXIT_CODE`；服务已退出或退出码非零时安装器以中文错误中止，不会打印“服务已启动”。服务账户保持 LocalSystem；需要专用账户时先准备权限，再执行：

```powershell
sc.exe config EdgePulseAgent obj= "DOMAIN\account" password= "<口令>"
```

注意：把服务账户口令写在 `sc.exe config ... password= "<口令>"` 里，会进入 PowerShell 历史与 WMI 可读的进程命令行，同机其他管理员可能读到。改用 `services.msc` 的“登录”页，或给服务配置 gMSA 或虚拟账户。

### 14.4 节点侧准备

安装器只创建目录与配置模板，不会复制证书。首次安装建议先不启动：

```powershell
powershell -ExecutionPolicy Bypass -File $env:TEMP\edgepulse-agent\install-agent.ps1 -NoStart
```

1. 把控制面签发给该节点的 `ca.pem`、`agent.pem` 与 `agent-key.pem` 复制到 `C:\ProgramData\EdgePulse\Agent\certs`（自定义 `-DataDir` 时为 `<DataDir>\certs`）。目录 ACL 已只允许 Administrators 与 SYSTEM，用管理员会话复制即可。
2. 编辑 `C:\ProgramData\EdgePulse\Agent\agent.yaml`：`agent.server.base_url` 指向控制面 9443 地址，`agent.server.name` 改成节点名，证书三项保持指向数据目录下的 `certs`。
3. 需要注册令牌时按 14.5 写入服务作用域环境变量。
4. 用 `sc.exe start <服务名>` 启动；默认路径下服务名是 `EdgePulseAgent`。

不先准备证书就启动时，Agent 会在身份加载阶段报错退出；安装器的启动校验会读取 `sc.exe queryex` 的状态与 `SERVICE_EXIT_CODE`，不会把已经退出的服务报告成启动成功。

### 14.5 注册令牌

令牌只从环境变量读取。服务进程的环境变量写在服务注册表项的 `Environment` 值里：

```powershell
reg add "HKLM\SYSTEM\CurrentControlSet\Services\EdgePulseAgent" /v Environment /t REG_MULTI_SZ /d "EDGEPULSE_AGENT_ENROLLMENT_TOKEN=<令牌>" /f
Restart-Service EdgePulseAgent
```

已有节点更换证书时改用 `EDGEPULSE_AGENT_REBIND_TOKEN`。注册成功后删除该值并重启：

```powershell
reg delete "HKLM\SYSTEM\CurrentControlSet\Services\EdgePulseAgent" /v Environment /f
Restart-Service EdgePulseAgent
```

注意：`Environment` 值以明文保存在注册表，能读取该键的管理员与 SYSTEM 都能看到令牌；设置后应尽快完成注册并删除。不要写进 `agent.yaml`、安装脚本或日志。

### 14.6 状态与日志

```powershell
sc.exe query EdgePulseAgent
sc.exe queryex EdgePulseAgent
Get-Content C:\ProgramData\EdgePulse\Agent\agent.log -Tail 50 -Wait
Get-EventLog -LogName System -Source "Service Control Manager" -Newest 20
```

`sc.exe query` 显示服务状态，`sc.exe queryex` 额外给出进程 ID、`WIN32_EXIT_CODE` 与 `SERVICE_EXIT_CODE`。服务以 `ERROR_SERVICE_SPECIFIC_ERROR`（1066）结束时，`WIN32_EXIT_CODE` 是 1066，Agent 自己的返回值在 `SERVICE_EXIT_CODE` 一行；常见原因是证书缺失、注册被拒或状态目录不可写，先看 `agent.log` 与事件日志。

```powershell
# 停止并删除服务、删除二进制，保留数据目录
```

### 14.8 升级

控制面下发 `agent.update` 后由 Agent 与安装器协作完成升级：

1. Agent 先对命令 `sha256` 的 32 字节摘要验证 Ed25519 签名，通过后下载归档并核对摘要与命令一致；随后把待上报结果写入状态库，然后启动 `powershell.exe -File <安装目录>\install-agent.ps1 -Upgrade <包> -HealthTimeout <秒> -StateDir <数据目录> -InstallDir <安装目录>` 并退出当前进程。
2. 安装器先拒绝 zip 里的绝对路径与 `..` 路径段，校验 `checksums.sha256`、manifest 版本与 `platform`；归档真实性已由 Agent 的签名检查建立。随后删除旧的 `update-health`、`update-rollback` 与 `update-expected`，再备份 `edgepulse-agent.exe` 为 `.previous`，停止 `EdgePulseAgent`，只替换 exe。替换后、启动服务前写入 `<数据目录>\update-expected`（内容为 manifest 版本）。替换前任何一步失败时 exe 不变，安装器会检查服务状态并重新启动已停止的旧服务，然后以退出码 1 结束。
3. 安装器启动服务，并在健康时限内等待 `<数据目录>\update-health` 的内容等于 manifest 版本。新版本 Agent 在首次成功心跳后写出该标记：有 `agent.update` 待上报结果时用成功结果替换此前“安装器已启动”的结果；手工 `-Upgrade` 没有待上报结果时，按 `update-expected` 的版本写健康标记。两种路径都会在版本匹配后删除 `update-expected`。
4. 成功时删除 `.previous`、健康标记与 `update-expected`。超时、启动失败或标记版本不符时，安装器停止服务、恢复 exe、删除 `update-expected`、写入 `update-rollback`（内容为目标版本）、启动旧服务，并以退出码 1 结束；旧版本 Agent 在首次心跳后把命令按失败写回结果队列（同样替换“安装器已启动”的结果）并删除回滚标记。若没有回滚标记但运行版本与升级目标版本不一致，Agent 也按失败上报，且不写健康标记；`update-expected` 与运行版本不符时只记 WARN 并保留标记，由安装器回滚。

配置、状态库、证书与安装脚本副本保持原样。安装器日志写入 `<数据目录>\update-installer.log`（默认 `C:\ProgramData\EdgePulse\Agent\update-installer.log`），安装器不写 SQLite。限制：升级模式固定服务名 `EdgePulseAgent`，不接受 `-NoStart` 或自定义服务名；必须以管理员身份运行；手工运行安装器只校验 `checksums.sha256`，不验归档签名，需要调用方自行确认归档来源；只有升级前后两个版本都包含本节的心跳确认逻辑时，回滚后的失败结果才会自动补报。

`agent.restart` 同样先入队并尝试上报结果，再启动脱离的 `powershell.exe -NoProfile -Command "Restart-Service -Name 'EdgePulseAgent' -Force"` 并请求当前进程停止。服务名固定为 `EdgePulseAgent`，自定义服务名不支持该命令；启动失败只记 ERROR 并保持运行。

### 14.9 服务冒烟（默认不运行）

`scripts\check-agent-windows-service.ps1` 默认只打印 `SKIP` 并以 0 退出，不创建任何服务；只有显式设置门控变量后才会以管理员身份执行完整生命周期：

```powershell
$env:EDGEPULSE_RUN_SERVICE_SMOKE = '1'
powershell -ExecutionPolicy Bypass -File scripts\check-agent-windows-service.ps1 `
  -ConfigPath agent\packaging\windows\agent.yaml.example -CertificateDirectory var\certs
```

脚本用 `EdgePulseAgentSmoke<PID>` 作为一次性服务名，在临时目录安装、启动并查询 `STATE : 4 RUNNING`，等两秒复核状态与 `SERVICE_EXIT_CODE`，随后停止并用 `-Purge` 卸载，最后删除临时目录；服务名与临时路径都带进程号或随机后缀，不会碰默认安装。`-ConfigPath` 默认是 `var\agent.yaml`，文件缺失时直接 SKIP；`-CertificateDirectory` 默认 `var\certs`，缺少 `ca.pem`、`agent.pem` 或 `agent-key.pem` 时同样 SKIP。脚本把注册地址改成本机一个未使用的回环端口，注册重试期间服务应保持 Running；它只验证服务生命周期，不要求连上控制面。
